# 一邮通（OneMail）开发计划

> 版本：v0.1（规划稿）｜日期：2026-09-28｜状态：待晨央确认技术选型后开工

## 一、项目定位

一款 Windows 桌面端的多邮箱聚合收信工具：

- 用户配置多个邮箱账户（QQ邮箱、163、Gmail、Outlook、企业邮箱等）
- 软件定时/实时接收各邮箱的邮件，**标注来源**（哪个邮箱、哪个账号收到的）
- 开机自启，常驻系统托盘，新邮件弹通知
- **内存和 CPU 占用极小**（目标：常驻内存 < 50MB，空闲 CPU ≈ 0%）

## 二、核心需求清单

| 编号 | 需求 | 优先级 |
|---|---|---|
| F1 | 多账户管理：添加/删除/启用禁用邮箱账户 | P0 |
| F2 | 收信：通过 IMAP 拉取邮件（含正文、附件列表） | P0 |
| F3 | 来源标注：每封邮件显示所属账户，界面按账户分组/筛选 | P0 |
| F4 | 新邮件通知：托盘气泡 + 可选提示音 | P0 |
| F5 | 开机自启：注册表 Run 项（可开关） | P0 |
| F6 | 低资源占用：IMAP IDLE 长连接推送，替代高频轮询 | P1 |
| F7 | 本地缓存：邮件索引存 SQLite，离线可看已收邮件 | P1 |
| F8 | 邮件查看器：阅读正文、下载附件、标记已读 | P1 |
| F9 | 安全存储：账户密码加密后落盘（非明文） | P1 |
| F10 | 发信/回复 | P2（二期） |

## 三、开发阶段划分

### 阶段 0：技术验证（1-2 天）
- 写最小原型验证：IMAP 连接 QQ邮箱/163（授权码登录）、IDLE 推送是否可用
- 验证 tkinter + pystray 托盘常驻的内存占用基线
- **产出：技术验证结论，确定最终技术栈**

### 阶段 1：收信核心（3-4 天）
- `core/`：IMAP 客户端封装（连接池、IDLE、断线重连）
- 多账户调度器：每账户一条独立轻量线程，互不阻塞
- 邮件解析：MIME 解析、正文提取（HTML→纯文本降级）、附件识别
- **产出：命令行可跑通的收信引擎，能打印"来源账户 + 新邮件"**

### 阶段 2：数据与配置（2 天）
- SQLite 邮件缓存（账户、邮件、已读状态）
- 配置文件（JSON）+ 密码加密存储（Windows DPAPI / keyring）
- **产出：重启软件后邮件记录不丢**

### 阶段 3：界面与通知（3-4 天）
- 托盘图标 + 右键菜单（打开主界面/立即收信/暂停/退出）
- 主窗口：左侧账户列表（来源标注），右侧邮件列表 + 阅读区
- 新邮件 Windows 通知
- **产出：可日常使用的完整版**

### 阶段 4：自启与打包（1-2 天）
- 注册表开机自启（设置里可开关）
- PyInstaller 打包单 exe（关闭控制台窗口，排除不必要依赖压体积）
- **产出：可分发的 OneMail.exe**

### 阶段 5：打磨（持续）
- 断网重连、账户认证失败提醒
- 性能调优：空闲时 CPU 归零验证、内存实测
- 日志与问题排查

## 四、里程碑与验收标准

| 里程碑 | 验收标准 |
|---|---|
| M1 收信引擎 | 两个不同邮箱同时收信，来源标注正确 |
| M2 可用版 | 托盘常驻、新邮件弹通知、重启后数据保留 |
| M3 发布版 | 单 exe、开机自启、空闲内存 < 50MB、空闲 CPU 0% |

## 五、风险与预案

| 风险 | 预案 |
|---|---|
| 国内邮箱 IMAP IDLE 支持不一（QQ/163 可能不推） | IDLE 失败自动降级为可配置间隔的轮询（默认 5 分钟） |
| Gmail/Outlook 需 OAuth2，仅支持授权码会挡住部分账户 | 一期做"授权码/应用密码"，OAuth 留二期接口 |
| 杀软误报 PyInstaller 打包 | 必要时改用嵌入 Python 的目录式发布 |
| 附件/HTML 邮件解析边界情况多 | 解析失败时保底展示原始文本，不崩溃 |

## 六、待晨央拍板的决策点

1. **界面形态**：主窗口 + 托盘（推荐）还是纯托盘无窗口？
2. **收信方式**：接受"IMAP IDLE + 降级轮询"的组合吗？（推荐）
3. **一期邮箱范围**：先支持国内邮箱（QQ/163/126）+ 任意 IMAP 账户，Gmail/Outlook 的 OAuth 二期做？（推荐）
4. **是否需要未读计数角标**显示在托盘图标上？
